# Augmented Theatre — a kit for making and driving a show

[Augmented Theatre](https://augmented-theatre.web.app) turns an audience's
phones into part of the stage design. During a performance a control computer
sends cues over the venue's own Wi-Fi, and every phone plays surtitles, video,
colour, vibration, torch, camera looks, spatial audio, shaders that listen to
the room, augmented-reality scenery, and one note each of a chord the whole
house sounds together.

This repository is the parts you can make yourself:

| | |
|---|---|
| [`ar-set/`](ar-set) | build an AR set — a thing that stands up on a printed picture |
| [`demo-show/`](demo-show) | generate a complete show's media from nothing |
| [`drive/`](drive) | deliver a show to the phones and run it, without the Dashboard; play the phones as an instrument |

Everything here is generated by the scripts in it. There is no sampled
footage, no stock photography and no third-party audio anywhere in this
repository, which is why it can be published, forked and rebuilt without
asking anyone.

## Try it in five minutes

You need [the audience app](https://augmented-theatre.web.app) on a phone, the
phone and your computer on the **same Wi-Fi**, and Python 3. Nothing else: the
AR set is committed, built.

```sh
python3 demo-show/make-demo-show.py                   # the media, and the AR set
python3 drive/atc-drive.py demo-show/show --deliver   # walk-in: onto the phones
python3 drive/atc-drive.py demo-show/show --run       # curtain: run the show
```

Or, with nothing to make and nothing to deliver, the phones as an instrument:

```sh
python3 drive/atc-drive.py --ensemble                 # a chord, a progression, three parts
```

Delivery and running are separate commands because they are separate events in
a theatre: the show goes onto the phones during walk-in, over minutes, and the
cues are fired at curtain. Either can be repeated on its own — deliver again
for a phone that arrived late, run again for the second house. Leaving both
flags off does one and then the other, which is for trying it at a desk.

The first command needs `ffmpeg`. It synthesises the media and copies the AR
set in beside it, so the show is one folder and the second command is one
command: a folder holding an `ar-set.json` is read as a set, anything else as
media, and the driver takes any number of either. When the set is raised the
drawing it stands on is opened on this computer, so you can point the phone at
the screen with nothing printed.

**Give it time.** Pre-staging is deliberately unhurried — a handset sleeps a
random moment of up to 30 seconds before it so much as asks for the manifest,
and up to 2 more before each asset, so that a full house does not arrive on the
server at once. The driver waits for the phones to say they hold everything
before it runs a cue, and prints what each one is still fetching. Raising a set
whose pieces have not all landed does nothing at all, silently, which looks
exactly like a broken cue.

Each cue is also announced on the phones themselves, as a line across the top,
before it fires, on iPhone and Android alike — so the demo reads from the handset rather than from this
terminal, and a cue that arrived but found nothing to do can be told from one
that never arrived: the words appear either way. Add `--debug` and each phone
also lists every cue it actually accepted, with its own address on the first
line, which is how one phone of several is told apart.

The set is scaled against the width of that drawing. Printed at 21 cm square it
is right as it stands; on a screen it is whatever size that screen makes it, so
measure the picture and say what you measured — `--marker-cm=14.5` — or the
figure stands too large or too small.

To rebuild the AR set yourself you also need [Blender](https://www.blender.org/download/)
(free):

```sh
python3 ar-set/make-ar-set.py                  # rewrites ar-set/demo-triadic-ballet/
```

`atc-drive.py` prints what it is doing and what the room is doing:

## What each part is

### `ar-set/` — making an AR set

An AR set is a folder. The phone recognises a printed picture (the **anchor**),
works out where it is in space, and builds the set on top of it.

```sh
python3 ar-set/make-ar-set.py          # anchor, model, films, score, ar-set.json
```

It writes `ar-set/demo-triadic-ballet/`, which is already in this repository —
so you can deliver the set to a phone (below) before installing Blender, and
run this when you want to change it.

**The anchor is the one that is already printed.** This set's drawing is the one
the Dashboard ships and the one published at
[augmented-theatre.web.app/downloads/demo-triadic-ballet-anchor.jpg](https://augmented-theatre.web.app/downloads/demo-triadic-ballet-anchor.jpg),
so `make-ar-set.py` keeps it rather than drawing another. A phone looks for the
picture named in the set it was given: a set carrying a *different* drawing is
simply never found on the sheet in the audience's hands, and it fails silently
— the cue goes out, the camera opens, nothing stands up. `--new-anchor` draws a
fresh one instead, which is what you want for a set of your own; print that one.

Whatever the drawing, it has to be *findable*: detail everywhere rather than
three flat shapes, no mirror symmetry (a symmetric design can be recognised the
wrong way round), hard contrast, no gradients. Print it 21 cm square — that is
the width the set is scaled against, declared as `widthMeters` in
`ar-set.json`.

`build-the-figure.py` builds the figure in Blender. It is a worked example, not
a general tool: it makes *this* set, and the way to make your own is to read it
and change the numbers — or to use **`prompt-demo-set.txt`**, which is the
prompt that rebuilds this set from a description. Give it to Claude and run what
comes back.

Four rules decide whether a set works on a phone, and all four are easy to get
wrong:

1. **Author in real metres.** The set is about 0.2 m tall because it stands on
   an anchor about that wide.
2. **Every animated bone points the same way as its parent**, so its rest
   rotation is identity. A bone at 180° to its parent is the quaternion
   antipode: glTF interpolates rotations linearly, so the exporter writes
   opposite signs on consecutive keys and the limb takes the long way round.
   For the same reason, never animate a full revolution — sway ±45° instead.
3. **Video surfaces are planes named `screen-left` / `screen-right`**, each
   carrying a custom property `video` naming its file, so the binding travels
   inside the model.
4. **Export glTF Binary with +Y Up OFF** (the phones want Z-up and do the turn
   themselves) and **Custom Properties ON**, or the video bindings are dropped.

The last one is invisible until it is on a phone. So is the second: the figure
looks right in Blender's viewport and swings the wrong way in the room. Check
it by printing the worst dot product between consecutive quaternion keys — any
value below zero is a sign flip.

> From Blender 4.4 an `Action` no longer has `.fcurves`; walk
> `action.layers → strips → channelbags → fcurves` instead, with a fallback for
> older versions. Both scripts here do.

### `demo-show/` — a show's media, synthesised

```sh
python3 demo-show/make-demo-show.py [outdir]
```

Writes a still, an animated GIF, a flat film, an equirectangular 360 film, a
chime, a spatial voice and an audio-reactive shader — one of each kind the app
can present, so every cue path gets exercised — and copies
`ar-set/demo-triadic-ballet` in beside them, since a set is part of a show like
anything else. The PNG and the WAV are written byte by byte in pure Python; the
rest is ffmpeg. Takes a couple of seconds.

Two of them are marked by name, the way the Dashboard marks them with a switch:

* **`voice-hrtf.wav`** — a name holding `hrtf` is delivered as a *spatial
  voice*: the phone places it in the room around the listener, follows the
  phone as it turns, and loops it until it is stopped. It is a headphone
  effect. Mono and dry, because the phone supplies the direction and the room.
* **`sphere-360.mp4`** — a name holding `360` is a look-around sphere.

**`bauhaus-listens.frag`** is a shader driven by each phone's own microphone,
so every phone in the house draws it differently and nothing about the room's
sound is sent over the network. It is **GLSL ES 1.00** (`#version 100`,
`gl_FragColor`, `texture2D`), and may declare only `uTime`, `uLevel` (0–1, this
phone's room sound), `uResolution` (the viewport in pixels) and `uCamera` (the
live camera, if it draws over it) — the driver reads which of those it declares
and puts that in the manifest, as the Dashboard's importer does. A Shadertoy
shader ports by renaming `iTime`, `iResolution` and `iChannel0`; `texelFetch`,
`switch`, unbounded loops and multi-pass shaders do not port. The phone asks
for the microphone the first time one is started, and starting one stops
whatever is playing, because a phone cannot listen to a room it is playing
into.

### `drive/` — running a show from Python

```sh
python3 drive/atc-drive.py demo-show/show --deliver   # walk-in: onto the phones
python3 drive/atc-drive.py demo-show/show --run       # curtain: run the show
python3 drive/atc-drive.py demo-show/show             # both, one after the other
python3 drive/atc-drive.py demo-show/show --listen    # just watch the phones
python3 drive/atc-drive.py demo-show/show --raise     # the AR set, and nothing else
python3 drive/atc-drive.py --ensemble                 # the phones as an instrument
python3 drive/atc-drive.py … --debug                  # each phone lists the cues it gets
python3 drive/atc-drive.py … --wait=60                # less patience with the room
python3 drive/atc-drive.py … --marker-cm=14.5         # the drawing, measured
python3 drive/atc-drive.py … --no-marker              # leave this screen alone
```

`--deliver` says what it actually achieved — a phone that never answered has
not been delivered to, and it says that rather than claiming otherwise. `--run`
asks the house what it holds, prints the answer and then cues, without waiting
for anybody: at curtain the show starts.

A minimal control app in one file, no dependencies. It:

* **serves the media** over HTTP — `GET /manifest.json`, `GET /asset/<sha256>`,
  with `Range` requests so an interrupted download resumes;
* **tells the phones to fetch it** with `/atc/manifest`, the pre-staging cue;
* **listens** on the telemetry port for `/atc/holding` and `/atc/progress`, and
  prints how many assets each handset holds and what it is still fetching;
* **fires the cues** in order, each announced on the handsets first as a title
  line, printing each one as it goes on the wire, and opens a set's drawing on
  this screen as that set is raised;
* **puts the phones in the show** with `/start/1` and takes them out again with
  `/stop/1`, as the Dashboard's House row does. A phone in the show drops the
  foyer's own controls, and if its owner puts it away it tells them the
  performance is going on without them;
* **plays the ensemble** at the end — see below.

An AR set folder is handled the way the Dashboard's importer handles it: the
pieces are delivered as ordinary assets, and the `.atcset` document that ties
them together — which drawing, which model, which film on which surface, how
wide the paper is — is written here and delivered with them. Without it the
phone holds the files and has nothing to do with them, and `/atc/raise` finds
no set.

A folder that **already** holds an `.atcset` is a set the Dashboard wrote, and
it is served exactly as it lies: the document's digests are the ones the phones
may already hold, so rewriting it would change its hash for nothing. That means
a show folder made by the Dashboard — media flat, each set in a folder of its
own — can be driven from here as it stands:

```sh
python3 drive/atc-drive.py ~/Shows/The\ Cherry\ Orchard/media
```

Assets are identified by **SHA-256** of their bytes; a phone never downloads a
hash it already has. Cues are broadcast to the interface's own broadcast
address *and* to 255.255.255.255, because the latter follows the default route,
which on a laptop is often not the Wi-Fi.

Nothing in it is a mock — it speaks the same OSC and the same HTTP as the
Dashboard, so the audience app cannot tell the difference.

## Cueing from something else

Any OSC sender will do — Isadora, Max, TouchDesigner, a Python script. A cue
is an address and some values, broadcast on **UDP 3000**. The full vocabulary,
with a photograph of an Isadora actor set up for each, is the
[reference on the website](https://augmented-theatre.web.app/#setup); these are
the ones worth knowing first:

```
/start/1     demo "Act One"               into the show: its files, a title line
/stop/1                                   back to the foyer
/text/1      "Tomorrow, and tomorrow" 40  a surtitle over whatever is showing;
                                          "" takes it off
/title/1     "Act One, Scene Two"         the line across the top
/atc/play    clip.mp4  1  0.5             a file, looping, to half the house
/atc/play/360 sphere-360.mp4              a look-around sphere
/atc/play/displace clip.mp4               the film bends the camera's picture
/atc/show    poster.png                   a still
/atc/stop    clip.mp4                     and stopped
/volume/1    0.3                          how loud, under a running clip too
/atc/hrtfpos voice-hrtf.wav 2 0 0         move a spatial voice: metres right,
                                          up, forward
/atc/raise   demo-triadic-ballet          an AR set stands up on its anchor
/atc/strike                               and comes down
/atc/audioreact 1 bauhaus-listens.frag    a shader driven by each phone's mic;
                                          0 to stop
/atc/effect  rain  1                      a look over the device's own camera:
                                          rain, heat, dziga, rain3d, camera,
                                          mirror; 0 to stop
/color/1     199 31 23                    every screen fills with one colour;
                                          /color/0 to stop
/vibrate/1   2000 250 1 40                a buzz, shaped: length and start in
                                          milliseconds, then repeat, then
                                          strength per cent — so 2 s long,
                                          starting 250 ms in, repeating, at 40%
/vibrate/0                                and stopped, everywhere
/debug/1                                  each phone lists the cues it receives;
                                          /debug/0 takes it away
```

**Numbers are read whatever type they arrive as**, because Isadora sends every
number as a float. The one thing a float can also be is the optional **share
of the house**, and that is told by its value: a float strictly between 0 and 1
is the share, and any other number is a parameter. So `0.5` is half the house,
and every phone is the absence of the argument. The share is rolled by each
phone, once per cue, so a half is scattered through the room rather than one
block of seats, and firing the same cue twice lights a different half.

**Every look can be stopped by the name that started it** — `/rain/0`,
`/dziga/0`, `/color/0`, `/camera/0` — and each of them ends whatever look is
running.

Delivery is separate from cueing: a cue only tells a phone to show something it
already holds. Deliver first — with the Dashboard, or with `atc-drive.py`. A
file is named by its filename or by its SHA-256. The name after `/atc/raise` is
the set's id, which is the folder's name in lower case; `atc-drive.py` prints
it as it delivers.

## The ensemble — the phones as an instrument

```sh
python3 drive/atc-drive.py --ensemble
```

Every phone has a small synthesiser in it. The console sends a **chord**, and
each phone plays **one note** of it, chosen from its own install id — so a
triad is spread across the room rather than sounded whole by every phone, and a
chord of one note is sounded by all of them. Nothing is delivered; the sound is
made on the phone from the numbers in the cue.

There are no note-on and note-off messages, because on Wi-Fi either can be
lost, and a lost note-off is a phone droning in a dark theatre with nothing
left that could stop it. The chord is sent as a **state** instead, again and
again, about three times a second, for as long as it should sound:

```
/midi/1                                   arm: start the audio, sound nothing
/midi/voice 0 9  100 127 900  400 70 450  1000 40 220
                                          the instrument: attack in ms, then up
                                          to four partials, each ratio (x100),
                                          level 0-127, decay in ms — a marimba
/midi/state 7 4000 100 40  60 64 67       the chord: revision 7, good for 4 s,
                                          gain 100, re-struck 40 times a minute,
                                          C E G — repeated about 3 times a second
/midi/0                                   silence; sent three times
```

* **The revision moves only when the chord changes.** A phone attacks when the
  set of pitches changes; a repeat with the same revision only keeps the chord
  alive. A phone ignores a revision lower than the one it holds, which is what
  makes late and duplicated UDP harmless — and why two senders cannot share a
  house: the higher count wins.
* **Stop sending and the phones fall silent** when the ttl runs out. That is
  the whole safety mechanism: no packet can leave a note sounding.
* **An empty chord is a rest**, and a pitch of `128` is how a patch sends one:
  it is outside MIDI's 0–127, so the phone reads no notes. A rest between two
  of the same note is what makes the second one strike again.
* **Every number in a `/midi/` cue is an int.** A float between 0 and 1 is
  read as the share, so a gain sent as `0.8` silences most of the room. Here
  the share is not rolled per cue: a phone decides once, from its install id,
  and the same phones stay in for the whole passage. Append it only below 1 —
  a trailing `1.0` is read as one more pitch.
* `/midi/voice 0 0` returns to the phone's built-in voice, a sine. The
  instrument is repeated alongside the chord, so a phone that joined late
  arrives at the right sound. The levels are relative: the phone scales them
  so they sum to one, then applies the gain.
* A phone that missed `/midi/1` arms itself on the first `/midi/state`, so the
  arm is sent once, not repeated.

**The house in parts.** A second float after the pitches is a **phase**, and
with the share it divides the house into parts that play different chords,
instruments and densities at the same time. A phone is in a part when
`(position + phase) mod 1 < share`, where `position` is the same stable hash of
its install id — so three parts are three cues of share `1/3` at phases `0`,
`2/3` and `1/3`, and every phone is in exactly one. Send the same share and
phase on that part's `/midi/voice`, or every phone takes whichever part's
instrument arrived last. Write the phase as `(n-k)/n`, never `1 - k/n`: they
differ by a rounding error, and a phase a hair under its share puts one phone
in two parts. The parts share no clock and drift against each other; that is
the character of the thing.

The `INSTRUMENTS` table in `atc-drive.py` holds the seven instruments the
Dashboard offers, with the numbers it sends for each.

## Background, transports and the network

* An **Android** phone keeps hearing cues with the app in the background, and
  says so in a notification. An **iPhone** does not; if it is put away during
  a show it asks its owner, a moment later, to come back. An app the user has
  swiped away hears nothing on either.
* The phones also accept the same OSC packets down a **TCP** connection to port
  3000, length-prefixed, which is what the Dashboard's TCP setting uses. UDP
  broadcast is all `atc-drive.py` needs.
* A **VPN** on the sending machine takes 255.255.255.255 into the tunnel and
  no phone hears anything. `atc-drive.py` also sends to each interface's own
  broadcast address for that reason; a patch should send to the network's
  directed broadcast (`192.168.1.255` on a /24) or have the VPN off.
* Guest and hotel networks usually isolate clients from each other, and then
  nothing works at all. Use a network of your own.
