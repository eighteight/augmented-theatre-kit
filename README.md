# Augmented Theatre — a kit for making and driving a show

[Augmented Theatre](https://augmented-theatre.web.app) turns an audience's
phones into part of the stage design. During a performance a control computer
sends cues over the venue's own Wi-Fi, and every phone plays titles, video,
colour, vibration, torch, camera looks, spatial audio and augmented-reality
scenery in step across the room.

This repository is the parts you can make yourself:

| | |
|---|---|
| [`ar-set/`](ar-set) | build an AR set — a thing that stands up on a printed picture |
| [`demo-show/`](demo-show) | generate a complete show's media from nothing |
| [`drive/`](drive) | deliver a show to the phones and run it, without the Dashboard |

Everything here is generated by the scripts in it. There is no sampled
footage, no stock photography and no third-party audio anywhere in this
repository, which is why it can be published, forked and rebuilt without
asking anyone.

## Try it in five minutes

You need [the audience app](https://augmented-theatre.web.app) on a phone, the
phone and your computer on the **same Wi-Fi**, and Python 3. Nothing else: the
AR set is committed, built.

```sh
python3 demo-show/make-demo-show.py                   # the media, and the AR set
python3 drive/atc-drive.py demo-show/show --deliver   # walk-in: onto the phones
python3 drive/atc-drive.py demo-show/show --run       # curtain: run the show
```

Delivery and running are separate commands because they are separate events in
a theatre: the show goes onto the phones during walk-in, over minutes, and the
cues are fired at curtain. Either can be repeated on its own — deliver again
for a phone that arrived late, run again for the second house. Leaving both
flags off does one and then the other, which is for trying it at a desk.

The first command needs `ffmpeg`. It synthesises the media and copies the AR
set in beside it, so the show is one folder and the second command is one
command: a folder holding an `ar-set.json` is read as a set, anything else as
media, and the driver takes any number of either. When the set is raised the
drawing it stands on is opened on this computer, so you can point the phone at
the screen with nothing printed.

**Give it time.** Pre-staging is deliberately unhurried — a handset sleeps a
random moment of up to 30 seconds before it so much as asks for the manifest,
and up to 2 more before each asset, so that a full house does not arrive on the
server at once. The driver waits for the phones to say they hold everything
before it runs a cue, and prints what each one is still fetching. Raising a set
whose pieces have not all landed does nothing at all, silently, which looks
exactly like a broken cue.

Each cue is also announced on the phones themselves, as a line across the top,
before it fires — so the demo reads from the handset rather than from this
terminal, and a cue that arrived but found nothing to do can be told from one
that never arrived: the words appear either way.

The set is scaled against the width of that drawing. Printed at 21 cm square it
is right as it stands; on a screen it is whatever size that screen makes it, so
measure the picture and say what you measured — `--marker-cm=14.5` — or the
figure stands too large or too small.

To rebuild the AR set yourself you also need [Blender](https://www.blender.org/download/)
(free):

```sh
python3 ar-set/make-ar-set.py                  # rewrites ar-set/demo-triadic-ballet/
```

`atc-drive.py` prints what it is doing and what the room is doing:

## What each part is

### `ar-set/` — making an AR set

An AR set is a folder. The phone recognises a printed picture (the **anchor**),
works out where it is in space, and builds the set on top of it.

```sh
python3 ar-set/make-ar-set.py          # anchor, model, films, score, ar-set.json
```

It writes `ar-set/demo-triadic-ballet/`, which is already in this repository —
so you can deliver the set to a phone (below) before installing Blender, and
run this when you want to change it.

**The anchor is the one that is already printed.** This set's drawing is the one
the Dashboard ships and the one published at
[augmented-theatre.web.app/downloads/demo-triadic-ballet-anchor.jpg](https://augmented-theatre.web.app/downloads/demo-triadic-ballet-anchor.jpg),
so `make-ar-set.py` keeps it rather than drawing another. A phone looks for the
picture named in the set it was given: a set carrying a *different* drawing is
simply never found on the sheet in the audience's hands, and it fails silently
— the cue goes out, the camera opens, nothing stands up. `--new-anchor` draws a
fresh one instead, which is what you want for a set of your own; print that one.

Whatever the drawing, it has to be *findable*: detail everywhere rather than
three flat shapes, no mirror symmetry (a symmetric design can be recognised the
wrong way round), hard contrast, no gradients. Print it 21 cm square — that is
the width the set is scaled against, declared as `widthMeters` in
`ar-set.json`.

`build-the-figure.py` builds the figure in Blender. It is a worked example, not
a general tool: it makes *this* set, and the way to make your own is to read it
and change the numbers — or to use **`prompt-demo-set.txt`**, which is the
prompt that rebuilds this set from a description. Give it to Claude and run what
comes back.

Four rules decide whether a set works on a phone, and all four are easy to get
wrong:

1. **Author in real metres.** The set is about 0.2 m tall because it stands on
   an anchor about that wide.
2. **Every animated bone points the same way as its parent**, so its rest
   rotation is identity. A bone at 180° to its parent is the quaternion
   antipode: glTF interpolates rotations linearly, so the exporter writes
   opposite signs on consecutive keys and the limb takes the long way round.
   For the same reason, never animate a full revolution — sway ±45° instead.
3. **Video surfaces are planes named `screen-left` / `screen-right`**, each
   carrying a custom property `video` naming its file, so the binding travels
   inside the model.
4. **Export glTF Binary with +Y Up OFF** (the phones want Z-up and do the turn
   themselves) and **Custom Properties ON**, or the video bindings are dropped.

The last one is invisible until it is on a phone. So is the second: the figure
looks right in Blender's viewport and swings the wrong way in the room. Check
it by printing the worst dot product between consecutive quaternion keys — any
value below zero is a sign flip.

> From Blender 4.4 an `Action` no longer has `.fcurves`; walk
> `action.layers → strips → channelbags → fcurves` instead, with a fallback for
> older versions. Both scripts here do.

### `demo-show/` — a show's media, synthesised

```sh
python3 demo-show/make-demo-show.py [outdir]
```

Writes a still, an animated GIF, a flat film, an equirectangular 360 film, a
chime and a voice — one of each kind the app can present, so every cue path
gets exercised — and copies `ar-set/demo-triadic-ballet` in beside them, since
a set is part of a show like anything else. The PNG is written byte by byte in
pure Python; the rest is ffmpeg. Takes a couple of seconds.

### `drive/` — running a show from Python

```sh
python3 drive/atc-drive.py demo-show/show --deliver   # walk-in: onto the phones
python3 drive/atc-drive.py demo-show/show --run       # curtain: run the show
python3 drive/atc-drive.py demo-show/show             # both, one after the other
python3 drive/atc-drive.py demo-show/show --listen    # just watch the phones
python3 drive/atc-drive.py demo-show/show --raise     # the AR set, and nothing else
python3 drive/atc-drive.py … --wait=60                # less patience with the room
python3 drive/atc-drive.py … --marker-cm=14.5         # the drawing, measured
python3 drive/atc-drive.py … --no-marker              # leave this screen alone
```

`--deliver` says what it actually achieved — a phone that never answered has
not been delivered to, and it says that rather than claiming otherwise. `--run`
asks the house what it holds, prints the answer and then cues, without waiting
for anybody: at curtain the show starts.

A minimal control app in one file, no dependencies. It:

* **serves the media** over HTTP — `GET /manifest.json`, `GET /asset/<sha256>`,
  with `Range` requests so an interrupted download resumes;
* **tells the phones to fetch it** with `/atc/manifest`, the pre-staging cue;
* **listens** on the telemetry port for `/atc/holding` and `/atc/progress`, and
  prints how many assets each handset holds and what it is still fetching;
* **fires the cues** in order, each announced on the handsets first as a title
  line, printing each one as it goes on the wire, and opens a set's drawing on
  this screen as that set is raised.

An AR set folder is handled the way the Dashboard's importer handles it: the
pieces are delivered as ordinary assets, and the `.atcset` document that ties
them together — which drawing, which model, which film on which surface, how
wide the paper is — is written here and delivered with them. Without it the
phone holds the files and has nothing to do with them, and `/atc/raise` finds
no set.

Assets are identified by **SHA-256** of their bytes; a phone never downloads a
hash it already has. Cues are broadcast to the interface's own broadcast
address *and* to 255.255.255.255, because the latter follows the default route,
which on a laptop is often not the Wi-Fi.

Nothing in it is a mock — it speaks the same OSC and the same HTTP as the
Dashboard, so the audience app cannot tell the difference.

## Cueing from something else

Any OSC sender will do; a cue is an address and some values on **UDP 3000**:

```
/atc/raise   demo-triadic-ballet          an AR set stands up on its anchor
/atc/strike                               and comes down
/atc/play    clip.mp4  1  1.0             a file, looping, to the whole house
/color/1     199 31 23                    every screen fills with one colour
/atc/effect  rain  1  1.0                 a look over the device's own camera
```

The optional extras are read **by type, not by position** — a float is the
share of the house (`1.0` is everyone, and each phone rolls its own dice, so a
half is scattered through the room rather than one block of seats), an int is
the loop regime (`0` plays once and holds the last frame).

Delivery is separate from cueing: a cue only tells a phone to show something it
already holds. Deliver first — with the Dashboard, or with `atc-drive.py`. The
name after `/atc/raise` is the set's id, which is the folder's name in lower
case; `atc-drive.py` prints it as it delivers.
